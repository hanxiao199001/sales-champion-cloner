## Problem Statement

房产中介公司老板是自己团队的销冠。他的销售能力（客户判断、异议处理、逼单技巧、选客户的直觉）全在他脑子里。团队没有系统化培训，新人自生自灭，成不成看天赋。公司的天花板 = 老板一个人的产能。他想"复制自己"，但没有工具把隐性经验变成显性的、可教的知识。

## Demand Evidence

- 有一个具体的房产中介公司老板，同时是销冠
- 他已经在录音收集自己的通话
- 目前完全凭个人经验和直觉做判断，没有结构化的方法论
- 团队基本没有培训体系，新人全靠自己摸索
- 核心痛苦：无法规模化自己的能力，公司增长受限于个人产能

## Status Quo

- 没有系统化培训
- 老板偶尔口头分享经验，但不成体系
- 新人自己摸索，成才率低
- 客户信息管理靠记忆和经验
- 老板的时间全花在自己卖房上，没精力系统带人

## Target User & Narrowest Wedge

**第一用户：** 这个老板自己。不是新人，不是其他中介公司。

**最窄切口：** 一个让老板上传自己录音、看到自己销售模式分析的工具。如果他看完说"卧槽，这就是我做的但我从没这么表达过"，产品成立。如果他耸耸肩，杀掉它。

## Constraints

- 录音是中文（普通话，可能带方言）
- 第一用户只有一个人（这个老板）
- 必须先验证"录音分析能让老板自己觉得有价值"这个假设
- 房产销售场景特殊：涉及带看、电话跟进、价格谈判等多种通话类型
- 已有竞品：DuDuTalk做房产销售录音分析（但定位是监控，不是知识萃取）

## Premises

1. **（修正后）** 录音中可提取的是销冠能力的"可教部分"（话术结构、异议处理模式、提问逻辑），但不是全部。选客户的直觉、语气节奏、现场判断力等隐性能力，需要通过老板批注等方式补充。产品是"起点"不是"完整方案"。
2. 老板真心愿意把核心能力系统化地分享出去，不是嘴上说说。
3. 新人拿到知识库后会主动学、能学会、能用在实战中。

## Cross-Model Perspective

Claude子代理独立审视（未看过对话）：

**最强版本：** 这不是录音分析工具，是"知识萃取引擎"。把一个人的隐性销售直觉变成组织级可用的结构化资产。做好了，公司从线性增长变成指数增长。

**关键洞察：** "第一用户是老板自己"是最重要的回答。V1必须是给专家看自己模式的工具，不是给新人的培训平台。如果老板在萃取过程中没有"aha moment"（"我原来每次成交前都做这个"），整个链条断裂。

**被挑战的前提：** 前提1。录音捕获的是文字表面，真正的成交能力可能在文字之外（选客户的眼光、语气节奏、现场判断力）。验证方法：跑20通录音的萃取，给老板看，如果他说"对但这不是真正原因"，前提不成立。

**48小时原型建议：** 单用户工具，上传录音→FunASR/SenseVoice转写→Claude API结构化分析（阶段识别、异议处理、成交技巧、模式识别）→跨录音Playbook汇总。三个功能，不多不少。

## Approaches Considered

### Approach A: 销冠镜子（最小可行）
单用户工具。老板上传录音→AI转写→结构化模式分析。
- Effort: S（人工: ~1周 / CC: ~3小时）
- Risk: Low
- Pros: 最快验证核心假设；投入极小；快速获得反馈
- Cons: 不直接解决"复制自己"的问题；没有团队功能
- Reuses: 开源转写模型（FunASR/SenseVoice），Claude API
- Completeness: 4/10

### Approach B: 销冠工厂（理想架构）
完整平台。录音萃取→结构化Playbook→新人培训界面→AI模拟练习→老板批注补充隐性知识。
- Effort: L（人工: ~2个月 / CC: ~3天）
- Risk: Medium
- Pros: 真正解决"复制自己"；包含老板批注机制补充隐性知识；可以卖给更多中介公司
- Cons: 未验证核心假设就大量投入；上线周期长；可能做了一堆没人用的功能
- Reuses: 同上 + 前端培训框架
- Completeness: 8/10

### Approach C: A→B阶梯（侧面切入）
分步走。先做A验证假设→老板确认后加批注功能→再扩展到新人培训界面。每一步验证后才进入下一步。
- Effort: 第一阶段S，全量M（人工: ~1个月 / CC: ~2天）
- Risk: Low
- Pros: 每步有验证不浪费；老板批注解决前提1风险；灵活调整方向
- Cons: 比直接做完整平台慢；需要纪律性地执行阶梯
- Reuses: A阶段代码完全复用到B阶段
- Completeness: 7/10（最终完成后与B相同，7分反映的是分阶段交付的风险——你可能在中间停下来）

## Recommended Approach

**方案C: A→B阶梯。**

理由：
1. 第一步（销冠镜子）直接验证最危险的假设——录音分析能否让老板自己觉得有价值
2. 老板批注机制（第二步）直接回应了前提1的修正——补充录音捕获不到的隐性知识
3. 每一步的产出都是下一步的输入，没有浪费的代码
4. 如果第一步就失败了，你只浪费了几个小时（用CC做的话），不是2个月

**阶段分解：**

| 阶段 | 产出 | 验证标准 | 预估时间(CC) |
|------|------|----------|-------------|
| A: 销冠镜子 | 上传录音→模式分析 | 老板说"就是这样" | ~3-8hr |
| A+: 老板批注 | 老板在AI分析结果上标注补充 | 批注内容有增量价值 | ~2-4hr |
| B: 新人界面 | 新人可浏览Playbook+老板批注 | 新人实际使用并反馈有用 | ~4-6hr |

注：阶段A的时间范围取决于ASR管线搭建顺利程度（GPU环境+FunASR中文适配+说话人分离）和Claude API中文提示词迭代轮数。全量约2-3天CC时间。

**未来可能的阶段（验证成功后再考虑）：**
- B+: AI模拟练习——新人跟AI练习销售场景。这是一个独立的产品方向（对话式AI+场景生成+评估体系），复杂度远超前几个阶段，放到验证完成后再评估。

**Playbook定义：** Playbook是一个结构化的销售模式集合，按类别组织（开场白、需求挖掘、异议处理、逼单技巧），每个模式包含：模式名称、出现频率、典型话术摘录、老板的批注补充。它是一个结构化JSON数据，在前端渲染为可浏览的知识库页面。

**技术选型（经工程审查确认）：**
- 中文语音转写：**阶段A用托管API**（阿里云语音服务或SenseVoice托管API）。不自建GPU基础设施。验证成功后阶段B再考虑自建FunASR。关键依赖：**说话人分离（diarization）**——必须区分老板和客户的对话。
- 内容分析：Claude API（结构化提取通话阶段、异议处理、成交技巧）。中文提示词工程需要多轮迭代，预留充足调优时间。**提示词工程是产品核心，不是实现细节。**
- 架构：**Python FastAPI 单体应用 + Jinja2模板**（不做前后端分离，阶段B再迁移Next.js）
- 存储：Supabase (Postgres + Storage)
- 认证：阶段A用密码保护URL即可，阶段B引入Supabase Auth
- 处理模式：**异步处理**——上传立即返回，后台任务处理ASR+分析，前端轮询状态
- 录音状态机：uploaded → transcribing → analyzing → done | failed（失败可一键重试）
- ASR质量门槛：转写置信度<80%时提示"录音质量不足，建议重录"
- Playbook更新策略：**增量更新**——新录音只添加新发现的模式，不重写已有内容（避免LLM非确定性导致内容漂移）
- 部署：Railway手动发布

**CC = Claude Code**，即用AI辅助编程的开发时间估算。

## Open Questions

1. 老板的录音是什么格式？手机录音？电话系统录音？质量如何？
2. 录音是纯电话还是也有带看现场的录音？现场录音噪音大转写准确率会低很多
3. 一个老板有多少通录音？需要多少通才能形成有意义的Playbook？（预估至少10-20通）
4. 隐私合规：录音是否经过客户同意？不同地区对通话录音有不同的法规
5. 这个产品做成了之后，卖给谁？只卖给这一个老板还是想做成SaaS卖给所有房产中介公司？
6. 定价模型：按录音数量？按月订阅？按团队人数？
7. 隐私合规：录音是否已经取得客户口头或书面同意？（这是法律前提，不是可选项）

## Success Criteria

1. **阶段A验证标准（5项具体检查）：**
   - [ ] 通话阶段识别准确——AI识别出的开场/需求挖掘/异议处理/逼单阶段，与老板手动标注的一致率≥80%
   - [ ] 异议处理模式识别——AI至少正确识别出3种老板常用的异议处理话术
   - [ ] 成交技巧提取——AI识别出的逼单方式，老板确认"是的，我确实这么做"
   - [ ] 跨录音一致性——不同录音中提取的同一模式描述一致，不自相矛盾
   - [ ] 意外发现——AI至少发现1个老板自己没意识到的行为模式（"aha moment"）
2. **阶段B验证标准：** 理想情况：对比两组新人（各至少3人），一组用Playbook，一组按原方式，3个月内统计人均成交量，Playbook组高30%以上。实际操作：小公司可能凑不齐对照组，退而求其次用"前后对比"——同一批新人，使用Playbook前后的成交率变化，或新人自评"这个对我有没有帮助"的结构化反馈
3. **商业验证标准：** 第一个老板愿意付费，并且愿意介绍给其他中介公司老板

## Distribution Plan

**阶段A（验证期）：** 部署为简单Web应用，给老板一个URL直接用。不需要分发渠道。

**阶段B及以后：** 验证成功后再规划分发渠道。过早设计SaaS分发没有意义——先让一个老板用起来。

**CI/CD：** 现阶段不需要复杂流水线。Railway手动发布即可（单体应用，无需Vercel）。

## Dependencies

- 中文语音转写模型的准确率（特别是房产��业术语、方言）。降级方案：如果方言转写准确率低于80%，退回到仅支持普通话转写，要求老板用普通话录音，或在转写后手动修正关键段落
- Claude API的中文理解能力和结构化输出质量
- 老板配合提供足够数量（10-20通）的高质量录音
- 隐私合规确认（前提假设：老板已取得或将取得通话对方的录音同意）
- 说话人分离（diarization）准确率——必须能区分老板和客户的对话，否则分析无法进行。降级方案：如果自动分离不准确，让老板手动标注"这段是我说的"

## The Assignment

**不是"去开发"。是这个：**

这周跟这个老板坐下来，手动做一次萃取。拿他3通录音，自己用通义听悟或飞书妙记转写，然后自己读转写稿，手动总结出他的模式——他怎么开场、怎么处理价格异议、怎么逼单。把总结拿给他看。

如果他的反应是"卧槽你怎么知道"或者开始兴奋地补充"对对对，还有这个我没说但我一直在做"——你的假设成立，值得写代码。

如果他的反应是"嗯...大概是这样吧"——你需要搞清楚到底缺了什么，是录音里信息不够，还是分析角度不对。

**先用手做一遍，再用AI做。**
